## 12주차 갑자기 큰 소리·격한 움직임·멀티모달 (TBD-5, FD-017, FD-018) — 문헌 초안

녹음이 아직 없어 문헌 기준으로 시작했습니다. 녹음이 오면 아래 "다시 맞출 것"을 실제 값으로 바꿉니다. 자세한 판정 방식은 [docs/api](../api/README.md#갑자기-큰-소리-fd-015-변경-tbd-5).

**갑자기 큰 소리** (`app/detectors/loudness.py`): YAMNet은 소리 종류 점수만 내고 음량을 출력하지 않아, 음량은 파형에서 직접 잽니다(0.1초 RMS dBFS).

| 확인 | 결과 |
|---|---|
| 처음 문헌 그대로(절대 음량 −30dBFS 이상) | 실패: 이 워치는 평소 말소리의 큰 순간이 이미 −9dBFS(말소리 구간 중앙값 −24dBFS) |
| 완전 무음 프레임을 배경에 넣음 | 실패: 녹음 시작·말 사이가 0이라 배경 −90dBFS → 모든 말소리가 "80dB 튐" |
| 고친 방식: 무음 제외 + 평소 말소리 대비 +16dB + 배경 대비 +15dB | 실제 워치 평소 말투 11창 모두 0.14점 이하, TTS 데모 13창 0.01 이하 |
| 실제 녹음 0.5초를 키워 고함 흉내 | +4dB 0.19 / +8dB 0.52(위험) / +12dB 0.71 |

**격한 움직임** (`app/detectors/motion.py`): 합성 신호로 규칙만 확인했습니다. 낙상(자유낙하 → 4g → 정지) 0.8 이상, 창 끝 낙상(정지 모름) 0.5~0.8, 충격만 4g 약 0.58, 걷기·뛰기 0.3 이하, 약한 착지 0.3 이하.

**멀티모달**: noisy-OR. 단독 신호는 전과 같은 판정, 애매한 두 신호(0.35 + 0.35)는 0.58로 위험.

**다시 맞출 것 (워치 녹음 요청)**
- 소리: 평소 대화, 고함·비명(가까이/멀리), 박수, 문 쾅, 물건 떨어뜨림, 길거리·버스·지하철 소음 → `AI_LOUD_OVER_SPEECH_DB`, `AI_LOUD_JUMP_DB`, `AI_LOUD_SPEECH_REF_DBFS`
- 움직임(워치 차고): 침대·매트에 넘어지기, 팔 휘두르기·뿌리치기, 걷기, 뛰기, 계단, 손목 털기, 박수 → `FREE_FALL_G`, `FALL_IMPACT_G`, `IMPACT_G`, `STRUGGLE_*`
- 녹음은 `samples/`(Git 제외)에 두고 결과 숫자만 이 문서에 적습니다.

## 11주차 FD-014 위험 음성 감지 (Whisper) 평가

한국어 TTS 161개(23문장 × 화자 4명 SunHi·InJoon·Hyunsu·Heami, 평상·다급 톤)로 평가했습니다. 문장은 위험 10개, 일상 6개, 헷갈리는 문장 5개("내가 도와줄게", "이제 그만 집에 가자" 등), 키워드가 그대로 든 일상 표현 2개("숙제 좀 도와줘", "장난 그만해")입니다.

조건: A 깨끗한 음성 / B 실제 야외 소음(ESC-50 엔진·비·발소리·경적) 10dB 속 10초 청크 / C 같은 10초를 워치 현재 형식인 1.5초로 자름 / D SDS 형식 5초·1초 겹침. 위험 판정 비율:

| 정답 | 방식 | A 깨끗함 | B 소음 10초 | C 워치 1.5초 | D SDS 5초 |
|---|---|---|---|---|---|
| 위험 문장 | 기존 (정확 일치) | 90% | 86% | 64% | - |
| 위험 문장 | **변경 (모음 1개 차이 허용)** | **94%** | **94%** | 70% | **96%** |
| 위험 문장 | 변경 + hotwords | 100% | 100% | 94% | 100% |
| 일상 문장 | 변경 | 0% | 0% | 0% | 0% |
| 일상 문장 | 변경 + hotwords | 0% | 0% | **12%** | 2% |
| 헷갈리는 문장 | 변경 | 0% | 0% | 3% | 3% |
| 헷갈리는 문장 | 변경 + hotwords | 0% | 3% | **29%** | **17%** |

- 말소리 없는 클립 41개(무음, 엔진·비·발소리·경적·기차·개·사이렌·유리 파손): 40개는 Whisper를 돌리지 않고 생략(무음 1, 말소리 없음 39), 지어낸 텍스트 0개, 위험 판정 0개.
- **hotwords는 기본으로 끕니다.** 탐지는 100%가 되지만, 짧은 청크에서 "살려고" → "살려줘"처럼 위험 문구를 지어내 일상 대화 오탐이 생깁니다. 오탐은 FD-019 확인 질문이 반복되는 문제로 이어집니다. 다른 신호(비명, 평소보다 큰 목소리)가 있을 때만 hotwords로 한 번 더 확인하는 2단계 방식은 검토할 만합니다.
- **청크 길이가 탐지율에 크게 영향을 줍니다**: 워치 1.5초 70% vs SDS 5초 96%. 문구가 청크 경계에서 잘리기 때문입니다. 백엔드·앱과 5초·1초 겹침 형식을 맞추는 것을 권장합니다.
- 남은 놓침은 Whisper 오인식입니다: "놔주세요" → "맞으세요/낮으세요"(자음 차이), "도와주세요" → "보여주세요", "그만해" → "꾸만해". 자음 차이를 허용하면 "봐주세요", "와주세요" 같은 일상 표현과 겹쳐 허용하지 않았습니다.
- 처리 시간: 깨끗한 음성 1개 평균 0.56초 (Whisper base, CPU int8).

## 11주차 FD-016 음성 개인화 (화자 임베딩·개인 기준값) 평가

화자 4명을 서로 다른 사용자로 보고 약 20초 등록 문장으로 프로필을 만든 뒤, 위 161개 문장(깨끗함, 10dB 소음)과 비교했습니다.

| 화자 | 기준 피치 | 기준 음량 | 다급한 톤의 변화 (본인 기준 대비) |
|---|---|---|---|
| SunHi (여) | 237 Hz | -16.5 dBFS | 피치 x1.14, 음량 +2.6 dB |
| InJoon (남) | 153 Hz | -20.5 dBFS | 피치 x1.18, 음량 +4.5 dB |
| Hyunsu (남) | 136 Hz | -18.2 dBFS | 피치 x1.15, 음량 +3.2 dB |
| Heami (여) | 203 Hz | -21.5 dBFS | (평상 톤만) 피치 x1.02 |

| 비교 (코사인 유사도 평균) | 본인 | 타인 |
|---|---|---|
| 평상 톤, 깨끗함 | 0.77 | 0.30 |
| 다급한 톤, 깨끗함 | **0.53** | 0.28 |
| 다급한 톤, 10dB 소음 | **0.41** | 0.24 |

- 다급하게 말하면 본인 유사도가 떨어져 타인과 겹칩니다. 화자 검증은 **본인일 때 점수를 더하는 데만** 쓰고 위험 판정을 막는 데 쓰면 안 됩니다(가해자 목소리일 수도 있음).
- TTS의 다급한 톤은 피치·음량을 일부러 올린 것이라 측정 방식 확인용입니다. 실제 사람 녹음으로 다시 확인해야 합니다.

```text
Safe Path - AI 파트 : Whisper(음성 탐지) + YAMNet(음향 분류) 세팅 정리
====================================================================

[개념 구분]
- Whisper  : 음성을 텍스트로 변환. "살려주세요" 같은 위험 문구 자체를 탐지.
- YAMNet   : 소리의 종류를 분류. 비명, 유리 깨지는 소리, 충격음 등 비언어 음향 이벤트 탐지.
- 두 모델은 담당 영역이 다르므로 하나의 오디오 클립에 대해 병렬로 돌리는 구조가 맞다.


====================================================================
1. Whisper 세팅
====================================================================

1) 설치
   pip install -U openai-whisper

   배포 단계에서 CPU로 돌릴 경우, faster-whisper(CTranslate2 기반, 동일 정확도에서
   최대 4배 빠름)를 추천.
   pip install faster-whisper


2) 모델 크기 선택

   모델    파라미터   속도(상대)   VRAM/메모리   용도
   tiny    39M        ~32x        ~1GB          실시간성 중요, 정확도 희생
   base    74M        ~16x        ~1GB          캡스톤 기본 추천
   small   244M       ~6x         ~2GB          정확도 더 필요할 때
   medium  769M       ~2x         ~5GB           CPU에선 부담 큼

   -> base로 시작, 위험 문구 인식률 부족하면 small로 상향.


3) 기본 사용 (openai-whisper)

   model = whisper.load_model("base")
   result = model.transcribe("clip.wav", language="ko")  # 한국어 명시 중요
   print(result["text"])


4) faster-whisper 버전 (배포용, 더 빠름)

   from faster_whisper import WhisperModel

   model = WhisperModel("base", device="cpu", compute_type="int8")  # int8이 CPU에서 빠름
   segments, info = model.transcribe("clip.wav", language="ko")
   text = " ".join(seg.text for seg in segments)


5) 위험 문구 탐지 로직

   DANGER_KEYWORDS = ["살려주세요", "살려줘", "도와주세요", "도와줘", "놔주세요", "그만해"]

   def detect_danger_phrase(text: str) -> bool:
       return any(kw in text for kw in DANGER_KEYWORDS)

   * Whisper가 오타/유사 발음으로 인식하는 경우가 있어, 추후 유사도 매칭
     (difflib 또는 자모 단위 비교)으로 보강하는 것을 고려.


6) 주의할 점
   - Whisper는 내부적으로 16kHz로 리샘플링해서 처리하므로 입력 샘플레이트는
     신경 쓰지 않아도 됨.
   - 짧은 클립(2~5초)일수록 문맥 부족으로 오인식이 늘어남. 5~10초 단위로 테스트 권장.


====================================================================
2. YAMNet 세팅
====================================================================

1) 설치
   pip install tensorflow tensorflow_hub numpy pandas


2) 모델 로드

   import tensorflow_hub as hub

   yamnet_model = hub.load('https://tfhub.dev/google/yamnet/1')


3) 오디오 입력 요구사항 (중요)
   YAMNet은 16kHz, mono, -1~1 범위의 float32 waveform만 받음. 반드시 변환 필요.

   import librosa

   waveform, sr = librosa.load("clip.wav", sr=16000, mono=True)  # sr=16000이 핵심


4) 추론

   import pandas as pd

   scores, embeddings, spectrogram = yamnet_model(waveform)

   class_map_path = yamnet_model.class_map_path().numpy()
   class_names = list(pd.read_csv(class_map_path)['display_name'])

   mean_scores = scores.numpy().mean(axis=0)
   top5_idx = mean_scores.argsort()[-5:][::-1]
   for i in top5_idx:
       print(class_names[i], mean_scores[i])


5) 위험 관련 클래스 필터링
   YAMNet은 AudioSet 기반 다수의 클래스를 출력. 클래스 개수나 이름은 모델
   버전에 따라 달라질 수 있으므로, 숫자를 하드코딩하지 말고 항상
   class_map_path()로 불러온 class_names에서 문자열 이름으로 검색해서
   사용할 것 (인덱스를 직접 믿고 접근하면 버전이 바뀔 때 조용히 틀린
   클래스를 잡는 버그가 생길 수 있음). 위험 감지에 쓸 만한 클래스만 추려서 체크.

   DANGER_CLASSES = [
       "Screaming", "Shout", "Yell", "Battle cry",
       "Glass", "Shatter", "Breaking",
       "Gunshot, gunfire", "Explosion", "Boom",
       "Smash, crash", "Thump, thud",
   ]

   def detect_danger_sound(scores, class_names, threshold=0.3):
       mean_scores = scores.numpy().mean(axis=0)
       hits = []
       for cls in DANGER_CLASSES:
           if cls in class_names:
               idx = class_names.index(cls)
               if mean_scores[idx] > threshold:
                   hits.append((cls, float(mean_scores[idx])))
       return hits

   * threshold(0.3)는 시작점. 실측 데이터로 조정 필요.

4. 입력 데이터 형식
====================================================================

[Whisper]
- 받을 수 있는 파일 : wav, mp3, m4a, flac, ogg 등 ffmpeg가 지원하는 거의 모든
  오디오 포맷 (내부적으로 ffmpeg 호출해서 디코딩).
- 내부적으로 실제 처리하는 형태 : 16kHz, mono, float32 waveform으로 강제 변환
  (원본이 44.1kHz 스테레오 mp3여도 알아서 리샘플링).
- 코드로 넣는 방법 3가지 :
    model.transcribe("clip.wav")            # 1. 파일 경로
    model.transcribe(audio_array)           # 2. numpy 배열 (float32, shape (n_samples,))
    # 3. bytes로 받은 경우 -> 임시파일로 저장 후 경로로 넘기는 게 무난함

[YAMNet]
- 딱 하나만 받음 : float32 numpy 배열, 16kHz, mono, -1.0~1.0 범위로 정규화된
  waveform. shape은 (n_samples,) 1차원.
- Whisper처럼 자동 변환 안 해주므로 직접 맞춰야 함.
    import librosa
    waveform, sr = librosa.load("clip.wav", sr=16000, mono=True)
    # librosa.load는 기본적으로 -1~1 정규화까지 같이 해줌

    # 원본이 int16 PCM(스마트폰 마이크에서 흔한 형식)인 경우
    waveform = pcm_int16.astype(np.float32) / 32768.0  # -1~1로 정규화

[실제 서비스 흐름 참고]
1. 폰 -> FastAPI : 오디오는 보통 wav 또는 m4a 파일(혹은 base64 인코딩)로 전송
2. FastAPI에서 받은 후 : 원본 오디오를 16kHz mono로 한 번 변환해두고
   - Whisper에는 파일 경로 또는 그 배열 그대로
   - YAMNet에는 float32 정규화까지 마친 배열로
   -> 입구에서 한 번만 16kHz mono로 통일해두면 두 모델에 개별 변환이 필요 없어
      코드가 깔끔해짐 (앞의 "샘플레이트 통일" 체크포인트와 동일한 이유).


====================================================================
5. 실시간으로 받을 때 문제되는 지점 (나중에 참고)
====================================================================
Whisper/YAMNet은 "한 문장을 다 듣고 해석하는" 모델이라 순수 실시간 스트림을
바로 흘려넣을 수 없음. 짧은 조각을 반복 처리하는 "주기적 업로드" 방식으로
갈 수밖에 없는데, 이 방식에서 특히 먼저 부딪히는 지점:

1) 청크 경계에서 소리/단어가 잘림 (가장 흔한 문제)
   - 5초 단위로 뚝뚝 자르면 "살려주세요"가 "살려" + "주세요"로 나뉘어
     둘 다 위험 문구로 안 잡힐 수 있음.
   - 해결 : 청크를 겹치게 자르기 (overlap)
       CHUNK_SEC = 5
       OVERLAP_SEC = 1  # 앞 청크와 1초 겹치게
     겹친 만큼 같은 소리를 두 번 탐지할 수 있으므로 타임스탬프 기준 중복 제거 필요.

2) 처리 속도가 실시간을 못 따라가면 백로그가 쌓임
   - 5초 오디오 분석에 7초가 걸리면 계속 밀려서 뒤늦게 알림이 갈 수 있음
     (안전 서비스에서 치명적).
   - 체크할 것 : 모델의 real-time factor. whisper-base가 CPU에서 5초 오디오를
     처리하는 데 몇 초 걸리는지 실측 후, 5초 미만이 아니면 tiny로 낮추거나
     GPU 검토.

3) 모델을 요청마다 다시 로드하면 느려짐 (흔한 실수)
   - FastAPI 엔드포인트 안에서 whisper.load_model()을 매번 호출하면 로딩
     시간(수 초)이 매 요청마다 추가됨.
   - 해결 : 서버 시작 시 한 번만 로드해서 메모리에 계속 들고 있기.
       from contextlib import asynccontextmanager
       from fastapi import FastAPI

       models = {}

       @asynccontextmanager
       async def lifespan(app: FastAPI):
           models["whisper"] = whisper.load_model("base")
           models["yamnet"] = hub.load('https://tfhub.dev/google/yamnet/1')
           yield

       app = FastAPI(lifespan=lifespan)

4) 무음 구간까지 다 분석하면 리소스 낭비
   - 사용자가 조용히 걷기만 하는 시간이 대부분인데 그 구간까지 계속 돌리면
     서버 자원 낭비.
   - 해결 : 가벼운 VAD(Voice Activity Detection)를 앞단에 두고, 소리가
     임계값 이상일 때만 본 모델로 넘기기 (webrtcvad 같은 초경량 라이브러리로 충분).

5) 동시 사용자 여러 명이면 한 대의 서버가 병목
   - Whisper/YAMNet 인스턴스 하나가 순차 처리하면 사용자가 늘수록 대기열이
     길어짐. 캡스톤 데모(팀원 몇 명 테스트) 수준에선 문제없음.
   - 참고만 해둘 것 : 나중에 필요해지면 워커 프로세스를 늘리거나(Gunicorn
     multi-worker), 큐(Celery/Redis)를 붙이는 식으로 확장 가능. 지금 단계
     에서 구현할 필요는 없음.

6) 네트워크 불안정 (모바일 환경 특성)
   - 걸어가면서 업로드하면 패킷 유실, 순서 뒤바뀜, 업로드 실패가 흔함.
     청크 하나가 유실되면 그 구간은 통째로 분석을 못 받음.
   - 해결 방향 : 업로드 실패 시 재시도 로직 + 청크에 타임스탬프를 찍어서
     순서 보장.
```

## 11주차 화자 검증 결합 평가 (TTS, 3초 창)

폰이 보내는 형식(소음 10dB, AAC 32kbps, 3초 창을 1초마다)으로 TTS 화자 4명을 각각 등록하고 161개 문장을 분석했습니다. 화자 검증은 본인 목소리가 평소보다 높고 클 때 위험도를 최대 0.15 올리기만 합니다(점수를 깎지 않음).

| 항목 | 결과 |
|---|---|
| 본인 유사도 (평소 말투 / 다급한 말투) | 평균 0.58 / **0.35** |
| 타인 유사도 | 평균 0.24 (최대 0.54) |
| 임계값 0.4에서 본인을 놓침 / 타인을 본인으로 | 32% / 6.6% |
| 흥분도 > 0인 창 (평소 / 다급) | 2% / 24% |
| 처리 시간 (3초 창 평균, 검증 없음 → 포함) | 0.37초 → 0.40초 |
| 판정 변화 | 오탐 증가 없음 (일상 문장 9→9창, 헷갈리는 문장 2→2창). 가산이 적용된 창은 7개 |

해석

- 문장 전체(본인 0.77)보다 3초 창에서 유사도가 크게 떨어지고, 다급한 말투는 0.35로 타인(0.24)과 많이 겹칩니다. 그래서 다급할 때 본인을 알아보는 비율이 낮아 가산이 거의 붙지 않았습니다. 2단계 등록(위급할 때 목소리를 목소리 특징에 더하기, `AI_ENROLL_MIX_URGENT`)이 이 문제를 겨냥합니다.
- 계산 비용이 작고(+0.03초) 오탐을 늘리지 않아, 켜 두어도 손해가 없습니다.
- TTS의 다급한 말투는 피치 ×1.15 정도로 실제 외침보다 약합니다. 유사도 임계값 0.4와 흥분도 범위는 **임시값**이며 실제 사람 녹음(평소·다급·타인)으로 다시 정합니다.
- 일상 문장 오탐 9창은 화자 검증과 무관하게 배경 소음(경적·엔진)에서 YAMNet이 낸 것입니다.
